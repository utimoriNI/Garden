# 思考管理アプリ構想

## 1. 背景

現在、自分の考え、価値観、内省、行動指針などを、主にObsidian上のMarkdownファイルとして蓄積している。

メモの粒度は幅広く、以下のようなものがある。

- 一言レベルの短いメモ
- 思いつきや感想
- 行動指針
- 音声対話を整理した長文ドキュメント
- 自分の価値観や考え方をまとめたノート

現状の課題は「書くこと」そのものではなく、書いた内容を後から見返し、関連付け、整理し、発展させることにある。

---

## 2. 作りたいものの方向性

作りたいのは、Notionのようにアプリ内へドキュメントを閉じ込めるツールではない。

ObsidianやローカルのMarkdownファイルを正本として保持しつつ、それらを読み込み、整理し、関連付け、再発見しやすくするための補助レイヤーを構築したい。

つまり、中心となるのは「新しい書き込みアプリ」ではなく、既存のMarkdown資産を活用するための思考管理・知識整理ツールである。

---

## 3. 重要な設計思想

### 3.1 データはMarkdownに保存する

アプリ内にデータを閉じ込めない。

- 正本はローカルのMarkdownファイルとする
- Obsidianから編集できるようにする
- Frontmatterで状態やメタデータを管理する
- 必要に応じてHTMLビューを生成する

### 3.2 Obsidianは「書く場所」として使う

Obsidianは、フリーティングノートやエバーグリーンノートを書く場所として十分に機能する。

一方で、Obsidian単体では以下の処理が難しい。

- 既存メモの一覧化
- フリーティングノート同士の関連付け
- フリーティングノートからエバーグリーンノートへの発展
- LLMによるタグ付けやFrontmatterの補完
- エバーグリーンノートのHTML化
- 自分の考えを後から見返すための専用ビューの提供

### 3.3 アプリの役割は「整理・接続・再発見」

このアプリは、文章を書くためのエディターではない。

主な役割は以下のとおりである。

- 既存ノートを読み込む
- ノートの状態を把握する
- タグやFrontmatterを補完する
- 関連しそうなノートを提案する
- フリーティングノートからエバーグリーンノートへの発展を支援する
- エバーグリーンノートを見返しやすくする
- 必要に応じてHTMLビューを生成する

## 4. 基盤とするモデル

### 4.1 エバーグリーンノートの考え方

今回の用途に最も近いモデルは、Zettelkastenやエバーグリーンノートの考え方である。

特に近い流れは以下のとおりである。

1. フリーティングノートを書く
2. 複数のフリーティングノートを見返す
3. 関連する考えを見つける
4. 考えを整理する
5. 長期的に残すエバーグリーンノートへ発展させる

ただし、一般的な知識管理とは目的が異なる。

今回の目的は、論文、記事、本などの成果物を作ることではなく、自分の思考、価値観、内省を整理し、長期的に育てることである。

そのため、通常のエバーグリーンノート運用を「自己理解・思考管理」に特化させる必要がある。

## 5. 想定ワークフロー

### 5.1 基本フロー

```text
思いつき
  ↓
フリーティングノート
  ↓
AIによる整理候補の提案
  ↓
人間による確認・修正・承認
  ↓
関連ノートとの接続
  ↓
エバーグリーンノート化
  ↓
HTMLビュー化・再閲覧
```

## 6. フリーティングノートに対するAI処理

フリーティングノートの作成後、LLMに以下の処理を任せる。

### 6.1 LLMに任せる処理

- タグ候補の提案
- Frontmatterの補完
- 関連しそうな既存ノートの提案
- Wikiリンク候補の提案
- 既存のエバーグリーンノートに統合できるかの判定
- 新しいエバーグリーンノート候補になるかの判定
- 内容の要約
- ノートの種類や状態の推定

### 6.2 人間が担当する処理

- AIによる提案の承認
- 不要なタグの削除
- 関連リンクの採用・却下
- エバーグリーンノート化するかどうかの判断
- 最終的な文章の編集
- 自分の価値観として残すかどうかの判断

**AIは編集者であり、人間は著者である。**

---

## 7. ステータス管理

AIが一度タグやFrontmatterを編集した後、人間が手直しする可能性がある。

このとき、次回AI処理を実行した際に、削除したタグや修正した内容をAIが再び復元してしまう問題が発生する。

そのため、AI処理の状態や人間による確認状況をFrontmatterで管理する。

### 7.1 状態管理の例

```yaml
status: fleeting
ai_processed: true
human_reviewed: false
```

より細かく管理する場合は、以下のようにする。

```yaml
note_type: fleeting
ai_status: suggested
review_status: pending
```

人間による確認後は、以下のように更新する。

```yaml
note_type: fleeting
ai_status: approved
review_status: reviewed
```

### 7.2 基本ルール

- `ai_status: suggested` のノートは、人間による確認待ちとする
- `ai_status: approved` のノートは、AIによる再編集の対象外とする
- `review_status: reviewed` のノートは、人間の判断を優先する
- AIは承認済みのFrontmatterを勝手に上書きしない
- AIは未処理または未承認のノートのみを処理対象とする

この方針により、AIによる自動化と人間による編集判断が衝突しにくくなる。

---

## 8. タグの使い方

タグは単なる分類ではなく、ノート同士を関連付けるための手がかりとして利用する。

### 8.1 タグの役割

- テーマを表す
- ノート間の関連性を見つける
- RAGやLLM処理における検索軸にする
- 後から一覧表示や絞り込みを行いやすくする

### 8.2 注意点

タグを増やしすぎると、管理コストが高くなる。

そのため、最初から完全なタグ体系を作るのではなく、AIに候補を提案させ、人間が承認する運用が適している。

## 9. ノートの関連付け

関連付けには、複数の手段を組み合わせる。

### 9.1 関連付けの材料

- Wikiリンク
- タグ
- Frontmatter
- 本文の意味的類似度
- 作成日時
- 更新日時
- ノートの種別
- エバーグリーンノートとの距離

### 9.2 LLMによる関連候補の提案

GitHub Actionsなどで定期的に処理を実行し、対象ディレクトリ内のMarkdownファイルを読み込む。

そのうえで、AIに以下を提案させる。

- 対象ノートと内容が近いノート
- 追加した方がよいWikiリンク
- 似たテーマを扱うエバーグリーンノート
- 統合候補
- 発展候補

---

## 10. GitHub Actionsによる自動処理

MarkdownファイルをGitで管理している場合、GitHub Actionsによって定期的に処理を実行する方法が考えられる。

### 10.1 処理対象

- フリーティングノート
- 未処理のノート
- AI処理済みだが未承認のノート
- 最近更新されたノート

### 10.2 自動処理の内容

- Frontmatterの補完
- タグ候補の追加
- 関連リンク候補の追加
- 要約の生成
- エバーグリーンノート化候補の抽出
- HTMLビューの生成

### 10.3 重要な制約

AIにすべての内容を直接書き換えさせるのは危険である。

初期段階では、以下のいずれかに限定するのが安全である。

- 提案ファイルを生成する
- 未承認のフィールドのみを更新する
- 本文を変更せず、Frontmatterと関連候補だけを更新する

---

## 11. HTMLビュー

エバーグリーンノートは、後から見返しやすくするためにHTML化する。

Markdownは編集に適している一方、読む体験という点ではHTMLの方が扱いやすい場合がある。

### 11.1 HTML化する対象

- 完成度の高いエバーグリーンノート
- 長期的に見返したい価値観ノート
- 自分の行動指針
- 共有したいドキュメント
- 読むことを重視するノート

### 11.2 HTMLビューに含める情報

- 本文
- 作成日
- 更新日
- ステータス
- 関連ノート
- 元のMarkdownを開くリンク
- 過去バージョンへの参照
- 「現在は採用していない」などの状態表示

---

## 12. ノートのライフサイクル

ノートには、作成後の状態遷移を持たせる。

### 12.1 状態の例

```text
fleeting
  ↓
processed
  ↓
reviewed
  ↓
evergreen_candidate
  ↓
evergreen
  ↓
deprecated / superseded
```

### 12.2 `deprecated` と `superseded` の扱い

過去には正しいと考えていたものの、現在は異なると考えている内容も残しておきたい。

そのため、過去のノートを削除するのではなく、状態を変更して保存する。

#### 例1

```yaml
status: deprecated
superseded_by: "[[新しい考え方のノート]]"
```

#### 例2

```yaml
status: superseded
current_note: "[[現在の考え]]"
```

これにより、自分の思考の変化を追跡できる。

## 13. アプリの本質

当初は、TwitterのようなタイムラインUI、HTMLビュー、ダッシュボードなど、見た目の設計から考えていた。

しかし、検討を進める中で、より本質的なのは以下であると分かった。

> 自分の思考メモを、AIの助けを借りながら、フリーティングノートからエバーグリーンノートへ育てるワークフローを構築すること。

UIの設計は、その後に行えばよい。

まず決めるべきなのは、以下の点である。

- ノートがどのように状態遷移するか
- どの段階でAIが介入するか
- どの段階で人間が確認・承認するか
- AIが編集してよい範囲はどこまでか

## 14. 最小実装案

最初はビューアよりも、AIによる整理ワークフローから着手するのが適している。

### 14.1 MVP

対象ディレクトリ内のMarkdownファイルを読み込み、未処理のフリーティングノートに対して以下を実行する。

1. Frontmatterを補完する
2. タグ候補を提案する
3. 関連ノート候補を提案する
4. エバーグリーンノート化の可能性を判定する
5. 人間によるレビュー待ちの状態にする

### 14.2 生成されるFrontmatterの例

```yaml
note_type: fleeting
status: processed
ai_status: suggested
review_status: pending
tags:
  - self-understanding
  - communication
  - values
related_candidates:
  - "[[会話における自信の持ち方]]"
  - "[[自分の価値観を言語化する]]"
evergreen_candidate: true
created: 2026-08-05
updated: 2026-08-05
```

### 14.3 レビュー後

人間による確認後、以下のように変更する。

```yaml
ai_status: approved
review_status: reviewed
```

AIは、これらの状態になったノートを勝手に再編集しない。

## 15. 今後検討すべき事項

### 15.1 ノート種別

初期段階では、以下の程度から始めるのが適している。

- `fleeting`
- `evergreen_candidate`
- `evergreen`
- `deprecated`
- `superseded`

### 15.2 AIが編集してよい範囲

AIに本文を書き換えさせるのか、Frontmatterだけを編集させるのかを決める必要がある。

初期段階では、本文には触れず、以下に限定するのが安全である。

- Frontmatter
- タグ候補
- 関連ノート候補
- エバーグリーンノート化候補

### 15.3 承認フロー

AIが提案した内容を、どの場所でどのように確認するかを決める必要がある。

候補は以下のとおりである。

- Obsidian上で確認する
- GitHubのプルリクエストとして確認する
- 専用のレビュー画面を作る
- Markdownに `review_status: pending` を付与し、後からまとめて確認する

### 15.4 HTMLビュー

HTMLビューは、最初からすべてのノートに対して作成する必要はない。

まずはエバーグリーンノートだけをHTML化し、その後、以下の機能を追加する。

- 関連ノートの表示
- 過去バージョンの表示
- `superseded` 関係の表示
- 思考の変化の履歴表示

## 16. 現時点での結論

現時点で作るべきものは、いきなり完成されたUIを備えたアプリではない。

まず構築すべきなのは、Obsidian上のMarkdown資産に対して、AIが以下を行うワークフローである。

- 整理
- 関連付け
- タグやFrontmatterの補完
- エバーグリーンノート化候補の提案

そのうえで、後から以下のビューを追加する。

- タイムラインビュー
- 関連ノートビュー
- エバーグリーンHTMLビュー
- レビュー待ち一覧
- `deprecated` / `superseded` の履歴ビュー

最初のMVPは、以下の仕組みに絞ることができる。

> フリーティングノートを読み込み、AIがタグ、Frontmatter、関連候補、エバーグリーンノート化候補を提案し、人間が承認する仕組みを構築する。

* 未処理のノート
* AI処理済みだが未承認のノート
* 最近更新されたノート

10.2 自動処理内容

* frontmatterの補完
* タグ候補の追加
* 関連リンク候補の追加
* 要約の生成
* エバーグリーン化候補の抽出
* HTMLビューの生成

10.3 重要な制約

AIに直接すべてを書き換えさせると危険。

最初は「提案ファイルを作る」か、「未承認フィールドだけを更新する」くらいが安全。

⸻

11. HTMLビューについて

エバーグリーンノートは、後から見返すためにHTML化したい。

Markdownは編集には向いているが、読む体験としてはHTMLの方が見やすい。

11.1 HTML化したい対象

* 完成度の高いエバーグリーンノート
* 長期的に見返したい価値観ノート
* 自分の行動指針
* 共有したいドキュメント
* 読むことを重視したノート

11.2 HTMLビューに含めたいもの

* 本文
* 作成日
* 更新日
* ステータス
* 関連ノート
* 元のMarkdownを開くリンク
* 過去バージョンへの参照
* 「この考えは今は採用していない」などの状態表示

⸻

12. ノートのライフサイクル

ノートには状態がある。

12.1 状態の例

fleeting
  ↓
processed
  ↓
reviewed
  ↓
evergreen_candidate
  ↓
evergreen
  ↓
deprecated / superseded

12.2 deprecated / superseded の扱い

昔は正しいと思っていたが、今は違うと思っている考えも残したい。

そのため、過去のノートを消すのではなく、状態を変える。

例。

status: deprecated
superseded_by: [[新しい考え方のノート]]

あるいは。

status: superseded
current_note: [[現在の考え]]

これにより、自分の思考の変化を追える。

⸻

13. 今回見えてきたアプリの本質

最初は、TwitterのようなタイムラインUIや、HTMLビュー、ダッシュボードなどの見た目から考えていた。

しかし、議論を進める中で、より本質的なのは以下だと分かった。

自分の思考メモを、AIの助けを借りながら、フリーティングからエバーグリーンへ育てるためのワークフローを作ること。

UIはその後でよい。

まず決めるべきは、ノートがどのように状態遷移し、どこでAIが介入し、どこで人間が承認するか。

⸻

14. 最小実装案

最初に作るなら、ビューアよりもAI整理ワークフローから始めるのが良さそう。

14.1 MVP

対象ディレクトリ内のMarkdownを読み込み、未処理のフリーティングノートに対して以下を行う。

1. frontmatterを補完
2. タグ候補を提案
3. 関連ノート候補を提案
4. エバーグリーン化できそうか判定
5. 人間のレビュー待ち状態にする

14.2 生成されるfrontmatter例

note_type: fleeting
status: processed
ai_status: suggested
review_status: pending
tags:
  - self-understanding
  - communication
  - values
related_candidates:
  - "[[会話における自信の持ち方]]"
  - "[[自分の価値観を言語化する]]"
evergreen_candidate: true
created: 2026-08-05
updated: 2026-08-05

14.3 レビュー後

人間が確認したら、以下のように変更する。

ai_status: approved
review_status: reviewed

AIはこの状態のノートを勝手に再編集しない。

⸻

15. 次に考えるべきこと

次に詰めるべき論点は以下。

15.1 ノート種別

* fleeting
* evergreen_candidate
* evergreen
* deprecated
* superseded

くらいで始めるのが良さそう。

15.2 AIが編集してよい範囲

AIに本文を書き換えさせるのか、frontmatterだけを編集させるのか。

初期段階では、本文は触らず、frontmatterと関連候補だけに限定するのが安全。

15.3 承認フロー

AIが提案した内容を、どこでどう確認するか。

候補。

* Obsidian上で確認する
* GitHub PRとして確認する
* 専用レビュー画面を作る
* Markdownに review_status: pending を付けておき、後からまとめて見る

15.4 HTMLビュー

HTMLビューは最初から全部作らなくてもよい。

まずはエバーグリーンノートだけHTML化する。

その後、関連ノート・過去バージョン・superseded関係などを表示する。

⸻

16. 現時点の結論

今作るべきものは、いきなり完成されたUIではない。

まず作るべきなのは、Obsidian上のMarkdown資産に対して、AIが整理・関連付け・エバーグリーン化の候補出しを行うワークフロー。

そのうえで、後から以下のビューを足す。

* タイムラインビュー
* 関連ノートビュー
* エバーグリーンHTMLビュー
* レビュー待ち一覧
* deprecated / superseded の履歴ビュー

最初のMVPはかなり絞れる。

フリーティングノートを読み込み、AIがタグ・frontmatter・関連候補・エバーグリーン化候補を提案し、人間が承認する仕組み。

ここから始めるのがよさそう。

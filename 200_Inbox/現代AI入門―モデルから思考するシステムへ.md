# 思考するシステムへ

## アブストラクト

### 背景と問題意識

AIは、モデルを大きくするだけで賢くなっているのだろうか。実際には、答えるときに使う計算や、ツール・記憶を扱うプログラムも性能に関わる。

### このノートの問いと結論

**AIの能力は、何によって伸びるのか？**

モデルを学習させる方法、答えるときの計算の使い方、ツールや記憶を扱う周辺プログラム。その組合せによって、AIができることや結果の正確さが変わる。

**計算や情報は、増やすほどよいのか？**

必ずしもそうではない。考え続けるうちに誤ったり、多数の候補から誤答を選んだりする場合もある。課題やモデルに合わせて、考える長さ、答えの選び方、情報の渡し方を調整する必要がある。

**AIが自分を改善できれば、それで十分なのか？**

改善案を作るだけでは不十分。よい変更を選べるか、別の課題でも有効か、費用に見合うかを確かめる必要がある。

### 読むと何が分かるか

AIがうまく働かないとき、モデルの能力に加えて、計算の使い方、渡す情報、使えるツール、結果の確かめ方を見直す視点が得られる。ただし、個別システムの改善方法をそのまま決められる手順書ではない。

## まず全体をつかむ

![学習・推論・ハーネス・自己改善の4つの観点](wiki-assets/thinking-systems/overview.png)

4つの観点（AI）

AIの能力には、モデルの学習、回答時の計算、外部ツールや記憶を扱うハーネスが関わる。ハーネスや学習方法は、AI自身による改善の対象にもなる。

モデルを大きくする話と、同じモデルをどう使うかという話を分けると、それぞれの工夫が何を変えるのかを追いやすい。

次の4つは実装の順番ではなく、AIの働きを分けて考えるための観点だ。

- 学習：モデルが能力を得るまでに、何へ資源を投入するか。
- 推論：目の前の問題へ、どれだけ計算を使うか。
- ハーネス：モデルに何を見せ、何をさせ、結果をどう確かめるか。
- 自己改善：改善案を誰が作り、どう選び、次の世代へ残すか。

## 1. 学習の規模と効率化

### 学習時スケーリング

学習時スケーリングでは、モデルと学習データを増やすことで、次に来るトークンを予測するときの誤差（予測損失）が減っていく。

ただし、同じ程度の改善を得るために必要な投資は次第に大きくなる。モデルやデータを増やし、長い入力を扱うには、計算量やメモリも必要になる。規模の拡大と並行して、計算やメモリの使い方を効率化する。

### 計算とメモリの使い方

![MoEは使う部分を選び、Loopは重みを再利用し、Attentionは参照先を絞る](wiki-assets/thinking-systems/efficiency.png)

効率化の模式図（AI）

- Sparse MoEは、トークンごとの処理でモデル全体を動かさず、一部のエキスパートを選んで計算する。モデル全体の容量を保ちながら、毎回使う計算を減らす発想だ。ただし、使わない部分も含めてモデルの重みを保持するため、必要なメモリが同じように減るわけではない。
- Looped Transformerは、同じ重みを使って繰り返し処理する。保持するパラメータを減らす狙いがあるが、繰り返す分の計算は必要になる。各周回で使うエキスパートを選び直すことが重要になる研究例もある。
- Sparse Attentionは、入力中のすべての要素を参照する代わりに、参照先を絞って計算する。何を参照するかに加えて、その計算をGPUで効率よく実行できる形にすることも課題になる。

多言語学習でも、データ量と予算の制約によって適切な学習戦略が変わる。

「軽い」といっても、計算が少ない、必要なメモリが少ない、実機で速い、という違いがある。どれを改善した話なのか確認したい。

## 2. 推論時の計算と停止判断

学習を終えたモデルでも、答えるときの計算の使い方を工夫できる。一度の生成で答えを決めず、長く考えたり、複数の答えを作って選んだりするのが、推論時スケーリングの考え方だ。ゲームで次の手を探索するように、言語モデルも候補を作り、評価しながら答えを探せる。

![原資料37枚目：推論時計算の直列・並列・ハイブリッドの比較](wiki-assets/thinking-systems/slide37.png)

[推論の3方式（引用）](https://speakerdeck.com/stillpedant/thinking-systems?slide=37)

- 直列では、ひとつの推論を長く続ける。
- 並列では、複数の回答候補を作り、多数決・採点・合成などで答えを決める。
- 探索型では、途中の候補を評価し、次に調べる経路を選ぶ。

ただし、推論を長く続けると、途中で誤る機会も増える。また、候補を採点する側も間違える。候補数を増やすほど、誤答が高く評価されて選ばれやすくなる場合がある。

そのため、計算をどこまでも増やすのではなく、**いつ止めるかを判断することが重要になる**。

### 答えの選び方と止め方

- Dynamic Early Exitは、推論の途中で仮の答えを出し、その確信度を推定して、考え続けるか止めるかを判断する。
- Best-of-Infinityは、集まった回答の分布から、多数決の結果が十分に安定したかを判断する。
- Tail-Tensionは、候補を採点して選ぶ場合に、誤答への過大評価によって結果が悪くなり始める候補数を推定する。

これらの研究手法は、すべてのモデル・問題へ同じ設定で使える万能策ではない。多数決の安定も、答えの正しさそのものを保証しない。

候補を作る能力と、よい候補を見抜く能力は別だ。「もっと考えて」と頼む前に、何を使って正しさを確かめるのかを決めるとよさそう。

## 3. ハーネスの役割と設計

![モデルが行動を選び、ツールを実行し、結果を次の行動へ戻すループ](wiki-assets/thinking-systems/harness-loop.png)

行動と結果のループ（AI）

AIハーネスは、モデルを呼び出し、その出力に応じて処理を進める周辺プログラムを指す。ReActのような構成では、モデルが行動を選び、外部環境で実行し、その結果を受け取って次の行動を選ぶ。

実際のシステムでは、モデルへ渡す指示や情報を選び、使えるツールと権限を決め、履歴を残す。履歴が長くなったときの圧縮や、失敗した処理からの回復、結果の評価も必要になる。同じモデルでも、こうした周辺プログラムの設計によって達成できる結果が変わる。

ブラウザを操作するAIに画面の状態を渡す方法には、画像、HTML、要素の役割や名前を表すアクセシビリティ情報などがある。方法によって、伝わる内容と情報量が異なる。

短くすれば常によくなるわけではない。多くの情報を扱えるモデルか、推論にどれだけ計算を使えるかによって、適切な渡し方も変わる。

ハーネスを、よいプロンプトの集まりだけだと捉えると、ツールの実行や失敗後の処理を見落とす。モデルに何を見せ、何を実行できるようにし、失敗したらどう回復するかまで含めて考える。

## 4. 自己改善の対象と評価

ハーネスはプログラムなので、AI自身が変更案を作り、実装し、結果を評価する対象にもなる。自己改善には、最新の状態を上書きし続ける方法と、過去の候補を残しながら改善案を探索する方法がある。

具体例は、会話の履歴が長すぎて処理が止まる問題への対応だ。履歴を要約してから再試行する処理を加えることで、停止していた処理から回復できるようにする。

ただし、周辺プログラムを書き換えることと、モデルの重みを更新することは別だ。モデルを改善するアルゴリズムをAIに作らせたり、事後学習の手順（パイプライン）をAIに組ませたりする研究もある。

自己改善には、よい案を作れるか、その中からよい変更を選べるか、別の環境でも役立つか、という課題が残る。何度も動かして評価する費用もかかる。また、評価上の点数だけがよくなり、期待した改善にならない危険もある。

Agent Behavior Mapsは、エージェントがどんな行動を選ぶかを評価し、その構成の性質を表す研究だ。まだ実行していない構成の性質を推定する試みもある。ただし、実際に動かして確かめる必要がなくなった、という意味ではない。

「自己改善できた」という報告では、何を変え、何を基準によい変更と判断し、改善に使わなかった課題でも結果がよくなったかを確認したい。特定のベンチマークでの改善は、無制限に自己進化できることを示すものではない。

## 持ち帰りたい見方

1. 性能が足りないとき、モデルの大きさだけでなく、推論予算・観測・ツール・評価のどこが詰まっているかを見る。
2. 計算や情報は増やすだけでなく、選び方と止め方を設計する。
3. 改善の主張は、費用・失敗例・評価条件・別課題での再現とセットで読む。
4. 自動化するほど、結果を確かめる手段と人が止められる境界を大切にする。
